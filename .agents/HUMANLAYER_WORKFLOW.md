# HumanLayer 三阶段流程：青云宗适配

2026-10-24，负责人选择“2：仅开发流程”。本文件是经筛选、重新编写的项目适配说明，不是上游原始SKILL.md、官方Codex插件或HumanLayer部署。未复制其整套技能，不增加技能目录，不改变现有24个技能。

## 与现有规范合并，而非再加一套工作流

Superpowers负责主流程；ECC提供按需影响分析/检索；Karpathy和游戏专项约束继续生效。HumanLayer只补充研究事实的可追溯性、阶段验证边界及恢复核对。AGENTS.md是入口；无需负责人在每次指令中指定HumanLayer。

适用：跨模块、多步骤、重大视觉试验及中断恢复。低风险小修复在现有计划或交付摘要写几行即可，不强制生成三份长文档。大任务仍遵守Superpowers设计/计划门禁；本配置不是新功能实施授权。

## 研究：说明当前事实，不把预期当现状

1. 按AGENTS读取主规划、当前任务、交接、变更、相关存档说明，核对Git分支/HEAD/工作树、Issue正文/评论/批准记录。
2. 沿调用链核对相关实现、数据边界、现有测试及真实运行结果。重要结论附文件/行号或日志/截图定位；引用行号发生变化时重新核实。
3. 区分“已证实”“尚未验证”“提出的建议”。研究现状时不顺便重构；用户要求诊断/优化时可以分析问题，但必须把诊断和建议与可复现事实分开。
4. 未追踪到的路径与缺失测试如实说明。外部资料只提供参考，不能证明本地已实现；不向外部服务上传私有源码、存档或凭据。

## 计划：每个阶段都有边界和验证方法

复用现有Issue、设计或验收文档；只有确实需要时才增加一份聚焦文档，链接回任务，不建立`.humanlayer/tasks/`或重复维护状态。

计划最低要说明：

- 本次目标、实施批准证据、不做事项和当前不确定性。
- 拟改文件、复用的代码/素材接口、受影响系统及存档影响。
- 可独立验证的阶段；每阶段具体自动检查和日志位置，适用的人工步骤。
- 停止条件：何时交给负责人看样、何时因重大差异需要确认、哪些后续工作尚未批准。
- 验证失败或方向被否定时如何保留旧成果；不以reset、覆盖他人改动或清档作为回退。

无论计划写得多新，都不能覆盖负责人最新决定、版本边界和存档保护。范围未变化的已批准工作不重复申请同一授权；新增重大取舍按原规则先确认。

## 实施：证据先于完成声明

一次只推进获批阶段，避免顺带清理或扩大功能。检查实际差异是否都服务于该阶段；与计划不符先查明原因，重大差异停下报告。

沿用现有测试入口、隔离APPDATA/存档、超时、退出码、PASS与错误日志联合检查。视觉任务检查游戏原生尺寸，而不是只看生成图；Windows导出/独立运行按现有交付规则执行，不因文档模板强制无关构建。

阶段交付分别说明实现、自动检查、实际运行、未执行项、已知问题和人工验收步骤。自动检查通过最多进入TESTED；负责人明确确认才可ACCEPTED。未经批准，不自动提交、推送、建PR或进入依赖该验收的下一阶段；批量批准仍不能自动转成人工验收。

## 中断恢复：核对证据，而非盲信勾选

先重新读取项目入口与当前Issue，再把旧勾选项映射到当前文件、提交/工作树及验证证据。缺证据的项标未验证；实现已变化则重跑受影响检查。不要仅凭勾选信任“已完成”，也不重做已确认且未受影响的工作。

GitHub Issues仍是具体任务状态主来源；TASKS只存快照与下一动作，AI_HANDOFF存恢复信息，CHANGELOG存实际变更。远端不可用须标注未同步。文档配置本身不改变V0.8游戏任务状态或验收进度。

## 上游内容的取舍

| 上游内容 | 本项目处理 |
|---|---|
| create-research：解释当前实现、文件定位、现有测试和开放问题 | 采用事实/推测分离及证据定位；保留本项目必须读取Issue的要求 |
| create-plan：目标、不做事项、分阶段及自动/人工成功标准 | 合并到已有计划和验收记录，不新增平行台账 |
| implement-plan：逐阶段验证并交给负责人确认 | 沿用本项目TESTED/ACCEPTED门禁，不照搬自动提交或专属代理 |
| 恢复时读取计划勾选 | 必须额外核对实际文件及测试证据，不直接信任勾选 |
| Linear、Claude Task专属代理、云端文档链接、工作树与提交模板 | 不安装、不启用、不虚构可用；本次不改任何全局配置 |
