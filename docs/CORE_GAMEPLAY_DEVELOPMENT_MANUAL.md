以下用于让方案具体可评审，尚不是用户逐项确认的规则：自动攻击；开局赠送1名核心弟子；先做剑修；固定竞技场；每局目标约8分钟；3种普通敌人、1个首领；约9～12项强化；首版无入场体力与门票；失败保留普通收益；炼丹仅少量确定配方；核心弟子之间暂不共享装备实例。实施受影响阶段前确认这些取舍，其他独立工作可继续。

## 2. 游戏目标与核心循环

定位：国风2.5D自由建造宗门经营，加玩家主动操作的俯视角肉鸽副本。继续使用现有Godot/GDScript项目，不为参考游戏改成3D或升级引擎。

循环：普通弟子生产 → 消耗资源建设与培养 → 核心弟子进入副本 → 操作躲避、选择局内强化 → 结算装备与培养材料 → 提升核心弟子、解锁下一阶段宗门发展 → 再次挑战。

首个完整版本必须使玩家能完成一次“准备—挑战—带回收益—产生可见提升—再次挑战”。宗门负责持续积累与准备，副本负责主动挑战、构筑与进阶，二者各有价值。

### 2.1 首版保留、新增与暂缓

| 系统 | 处理 |
| --- | --- |
| 木材、灵石、灵谷，生产与人口 | 保留并验证收支 |
| 现有七类建筑及升级、领地 | 保留，恢复自由建造表现 |
| 普通弟子招募、岗位 | 保留；不扩生活需求与随机天赋 |
| 修炼、境界 | 保留基础，明确普通与核心弟子用途 |
| 三部位、三品质装备与打造 | 保留；适配核心弟子，旧穿戴不丢失 |
| 核心弟子与主动副本 | 本轮主要新增方向 |
| 丹药、功法 | 只在完整战斗循环后加入最小内容集 |
| 原自动挂机与离线收益 | 保留兼容；重新确定与主动副本的奖励边界 |
| 多级加工、范围加成、复杂科技树 | 暂缓 |
| 装备洗练、随机词条、本命法器、五行炼制 | 暂缓 |
| 多副本体系、随机路线、复杂房间生成 | 暂缓，先做好一个副本 |
| 商店、额外货币、宗门竞争、神兽、道侣、联机 | 暂缓 |
| 角色行走采集动画、全图美术重制 | 不作为核心循环阶段前置条件 |

“暂缓”不代表删除现有功能；禁止以简化为由删除旧存档中的数据。

## 3. 宗门建设与资源规则

### 3.1 自由建造

复用已有网格投影、合法性、占用、区域解锁、资源扣除、施工、升级与拆除逻辑，普通入口恢复自由选择合法空格放置建筑。首版保持现有12×8逻辑范围、104×52投影及区域配置，不同时扩图或引入多格建筑。

主殿暂沿用现有固定锚点，其他功能建筑自由放置；“主殿也可移动”单列待确认，不推定已授权。移动已建建筑、旋转、道路编辑、装饰加成均不作为恢复自由建造的必需内容。

当前固定院落的烘焙地形不能只切开关后直接作为完成证据。恢复时必须处理：无建筑地形、旧院落残留、自由位置建筑脚点、尺寸、影子、前后遮挡、屋顶拾取、施工架和选择卡片。优先复用可用资产；画面不完整时明确标临时版本。候选29及局部样板保留为历史对照。

旧建筑按原ID、类型、格坐标、数量、等级、工期恢复，不能为了画面把旧建筑重新分配位置。普通模式新建不预赠演示建筑；演示入口继续使用独立存档。

### 3.2 资源职责

| 资源/内容 | 来源 | 主要消耗/用途 |
| --- | --- | --- |
| 木材 | 普通弟子生产，副本少量补充 | 建设与升级，既有打造 |
| 灵石 | 普通弟子生产，既有奖励 | 招募、建设、既有打造；后续可用于培养加速 |
| 灵谷 | 普通弟子生产 | 人口持续消耗及既有消耗 |
| 装备 | 既有打造/挂机掉落，后续副本 | 核心弟子战斗属性 |
| 进阶材料 | 拟由主动副本首领/明确进度奖励提供 | 后续突破或关键发展；先定义用途再新增 |

首版不一次引入石材、铁矿、板材、砖、锭等多级材料链。新增材料必须有稳定ID、唯一职责、来源、消耗、库存与存档规则。不能只增加掉落而没有使用出口。

### 3.3 生产与粮食

普通弟子采用建筑与岗位自动生产，不模拟行走采集。岗位、容量、成员集合一致。开局先允许沿用既有基础资源点，不能出现“没有采集建筑无法生产、没有资源无法建采集建筑”的死锁。

现有每名弟子每分钟1灵谷作为基线记录，不因手册擅改；缺粮生产倍率0.5已确认。是否将核心弟子计入粮耗、是否影响修炼、出战期间是否消耗，须在阶段3明确；未确认前不擅自扩大缺粮影响。普通弟子不因缺粮死亡，补足粮食后自动恢复生产。

必须展示：库存、每分钟产出、消耗和净变化，粮食预计可维持时间。负净收入需说明原因。30分钟预警仅为可调建议，不是已实现事实。

平衡表至少覆盖开局、第一次扩容、第一名核心弟子培养、首次副本通关四个节点。副本基础资源收益不能长期全面压倒同阶段宗门生产；不在设计期武断固定比例，应以相同时间窗口实测比较。

## 4. 普通弟子与核心弟子

### 4.1 普通弟子

承担采集等宗门工作，保留招募、人数上限、现有修炼与生产加成兼容能力；暂不新增天赋、体力、心境、关系、寿元。新流程不把普通弟子作为主动副本可选角色。

### 4.2 核心弟子

建议首版开局提供1名剑修，先验证一人完整培养和出战，不做抽卡、保底、碎片招募。数据区分核心/普通身份，稳定ID不与旧弟子冲突。是否沿用崔云川/周墨需确认；现有视觉角色预览不等于已实现核心弟子数据模型。

核心弟子需要：身份、姓名、职业、境界、修为、装备引用、已学功法、丹药使用状态和活动状态。只为实际启用的功能增加字段，不预建复杂模型。

入场时生成战斗属性快照，局内不随宗门换装实时变化；副本期间该角色不能同时修炼、参加旧挂机或重复入场。离场恢复可用状态，不丢装备与境界。暂不增加队友AI或三人主动战斗。

### 4.3 旧角色过渡

禁止直接把旧参战弟子改成生产身份并清空装备。阶段0提出迁移方案：旧普通弟子/旧挂机按兼容逻辑保留；新增核心弟子走新流程；如需身份转换，必须由玩家明确操作且有可验证映射。迁移前后核对ID、境界、修为、装备归属、岗位、队伍、资源。

## 5. 培养、装备、丹药与功法

### 5.1 成长分层

永久成长：境界、穿戴装备、已学功法、宗门设施效果。局内成长：本局等级、经验、强化与临时状态。离场清除局内成长，结算后永久状态仍可读档恢复。

基础修炼不持续消耗灵石；灵石与丹药加速为拟扩展。当前代码突破只消耗修为；“突破必须有丹药”属于待实施规则，不能将其误写成现状。建议仅大境界突破考虑丹药，小层级沿用修为，避免每次小提升都卡材料；最终边界需确认。

### 5.2 装备

先沿用武器、衣服、戒指与普通/稀有/史诗三品质。一个实例只归属一名角色的一个合法部位，库存上限沿用当前60件，不能让核心与普通角色重复穿戴同一实例。

首版不增加强化、洗练、随机词条、套装或分解货币。库存满必须给出明确处理：建议不丢弃已获得装备，阻止继续产生无法容纳的新装备并提示整理，或采用待领取容器；最终方案在奖励阶段选定并测试，不允许静默吞掉掉落。

### 5.3 丹药与功法的最小集

丹药放在战斗循环成立后接入，建议只做修炼加速与突破两类，每类少量配方。先明确原料来源、数量、制作工期、库存、使用效果，再确定是否新增药材与炼丹设施。首版可手动下单、计时完成，不做自动补货、药材年份、耐药性和炼制失败。

功法先服务战斗流派。建议一个基础攻击功法与少量被动，不做全品质大图鉴、多功法槽位和复杂搭配。永久学习解锁基础能力，副本三选一增强本局表现；同一效果不可在多个系统重复无上限叠乘。

### 5.4 参考数据录入规则

用户允许参考《山门与幻境》的装备、丹药、功法名称与详细数据；目前尚未整理或核验具体条目。实施时按批次查阅官方或相关Wiki资料，只取首版所需内容，不提前建立全量数据库。

每条记录包括：内部ID、显示名称、类别、来源URL、查阅日期、来源版本/未知标记、原始数值、单位、项目采用值、修改原因、效果定义、来源与消耗条件。原始数据和本项目数值分栏，不能混淆。

数值需适配当前每秒/每分钟单位、属性公式和副本时长；参考游戏的攻击数值不能未经换算直接覆盖当前属性。具体内容名核验后再写入配置，不把临时示例当原版事实。图片、图标、模型、音效和长描述不因允许参考名称数值就自动取得使用授权；沿用项目素材来源登记规则，不直接搬运整套资产。

## 6. 主动副本玩法

### 6.1 首个可玩副本建议规格

先做一张固定竞技场，目标约8分钟，3种普通敌人、1个首领，约9～12项局内强化。上述数量为范围上限参考，先以最小原型验证手感，可减少但不自动扩大。分房间、随机路线和多个专属副本待首个循环验收后再讨论。

操作建议：WASD移动，自动朝有效目标攻击；选择强化与暂停菜单时停止战斗。首版通过走位躲避，独立冲刺/无敌翻滚不是已确认必做项。鼠标用于界面选择，必要信息不能仅靠特效表达。

首局流程：选择核心弟子 → 查看境界/装备/功法和奖励预览 → 入场 → 清怪获得经验 → 升级暂停三选一 → 应对逐渐升级的敌人组合 → 首领 → 胜利或失败结算 → 返回宗门。

### 6.2 战斗与构筑要求

普通敌人至少形成追击、远程预警、冲锋等不同压力，先实现一种再逐步增加。攻击命中、受伤、死亡与首领预警清楚，敌人不得在玩家脚下无预警生成。

强化至少形成两种可感知打法，如飞剑穿透与环绕防护；名称仅为项目效果示例。强化记录适用技能、等级上限、互斥与前置条件。达到上限的选项不重复出现，不出现角色无法使用的空选项；候选不足三个时提供有效替代，不空窗卡住。

持续输出、范围、攻速、数量、穿透等属性设边界；明确伤害公式、最小伤害、攻击间隔下限和叠加顺序。永久属性与局内增益经统一入口计算，UI不复制公式。

### 6.3 状态和时间

状态至少区分：准备、战斗、强化选择、暂停、胜利、失败、待结算、已结算。敌人、计时与伤害由战斗模拟决定，动画只表现。暂停不推进冷却、刷怪与伤害，不能用关掉界面继续累计时间来跳过战斗。

建议副本运行时宗门按正常游戏时间生产，强化选择/全局暂停时一并暂停宗门，避免暂停刷资源；退出应用后只结算既有允许的宗门离线收益，绝不把主动副本离线模拟成胜利。此时间策略阶段0确认后统一实现，不能每个系统各算一遍。

### 6.4 胜败、退出与奖励

建议首版无门票/体力；失败保留本局已确认的普通收益，不发首领通关奖励，不扣永久境界与装备。首次通关奖与重复通关奖分开记录。关键进阶材料有确定来源，不完全依赖低概率掉落。

每局具有唯一运行ID，奖励经统一结算入口一次发放。重复点击、重进结算页、重读存档、保存失败重试不得重复发奖或只扣不发。背包满、非法物品、写盘失败有明确提示与回滚。

建议首版不做局内断点续玩：正常退出或崩溃后回宗门，未持久化本局不发奖，已完成持久化结算不重复发。入场前保存永久状态，启动恢复时清除悬挂出战锁。若选用其他恢复规则，先改本节再开发，不以失败方案临时决定玩家损失。

## 7. 原挂机、离线与主动副本的边界

原三人自动战斗不等于主动副本。先保留旧队伍和奖励兼容，不直接删除或把旧胜场解释成新副本通关。新核心弟子不得绕过活动互斥。

新主动副本承担操作挑战、构筑和关键进阶；旧挂机承担兼容及基础收益。现有每5胜装备掉落与主动装备掉落可能重叠，阶段6必须比较收益并提出调整，不在文档阶段直接改旧奖励。

离线资源生产、施工、修炼等复用现有最多8小时机制；主动副本不生成离线胜场。检查进出副本和暂停恢复是否重复推进宗门时间或重复结算离线窗口。

## 8. 开发阶段顺序

阶段号P0～P8表示依赖顺序，不是新的游戏版本号，也不表示所有阶段已批准开工。V0.8未验收与主动副本新范围分开记录；后续版本号与Issue范围经负责人确认再落地。

| 阶段 | 主要产出 | 前置 | 进入下一阶段的证据 |
| --- | --- | --- | --- |
| P0 基线与设计冻结 | 旧状态备份、决策表、迁移与时间方案、阶段任务范围 | 本手册评审 | 基线可运行，关键规则明确 |
| P1 自由建造恢复 | 普通模式自由放置与完整交互 | P0 | 双尺寸实际操作与旧坐标恢复正确 |

| P3 核心弟子与养成底座 | 独立身份、首个角色、装备与活动互斥 | P0、P2 | 旧角色不丢失，新角色可稳定保存 |

确认第11节决策，画出资源来源/用途和入场—战斗—结算状态。只为当前获批阶段建/更新Issue，不批量生成所有未来细任务。当前候选29保留，不把恢复自由建造理解为接受旧固定院落。

### P2：资源发展与新手目标

依据当前 resource_catalog、building_catalog、territory_catalog、development_goal_catalog 和 GameState 记录真实公式。先测基线，再调整获批数值，改动集中配置，不在多个UI硬编码。

围绕采集、人口扩容、修炼、装备准备和首次主动挑战组织发展目标；原目标中“10场挂机胜利”等不直接换成新副本通关，新增目标与旧领取标记分别兼容。

验收：缺粮与恢复、资源不足提示、建筑投资回报、离线资源守恒；开局无需等待高级副本掉落即可生产和发展；首次主动挑战无需长时间被动等待。以实测记录首轮关键节点时间，不先承诺未测完成时长。

### P3：核心弟子与养成底座

先确定身份存储方案与旧装备归属。可在现有稳定ID体系扩展身份，或独立集合引用；由影响分析选择最小兼容方案，不直接重写整个GameState。新增字段与迁移测试先行，再接角色面板。

验收：获取一次不重复赠送；普通弟子不进入新副本选择；核心角色换装与属性一致；出战/修炼/挂机互斥；旧档导入、异常身份和重复装备引用拒绝并回滚。

### P4：战斗手感原型

独立俯视角战斗场景，先用临时可辨识素材。只实现一个基础攻击、一种敌人及移动/受伤/死亡，不先做大技能表。选择并核验实际Godot节点/API，不沿用经营地图Control绘图去承担整套实时碰撞。

验收：移动方向速度一致，无穿墙/出界；攻击间隔与伤害一致；有无目标行为明确；攻击预警可躲避；暂停无伤害；真人试玩记录操作反馈。无头测试不能代替手感判断。

### P5：形成完整单局

加入经验获取、升级队列与三选一、敌人波次、首领、结束条件。先做约9～12个有效强化，再考虑数量；强化必须能完成两种打法。

验收：连升多级不丢选择、无非法候选/空选项、上限生效；首领只触发一次；胜利失败互斥；清场正确；重开不残留投射物、计时器或强化；达到目标敌人数时性能可接受。

### P6：接通资源与副本

接入出战快照、退出恢复、普通/首领/首通奖励与持久化运行ID，防重复结算；定义背包满处理和旧挂机收益边界。副本结果通过数据层发放，不由战斗UI直接改宗门库存。

验收：正常胜利、死亡、退出、崩溃恢复、重读与存盘失败；至少两轮完整成长；同时间窗口比较生产、挂机与主动副本收益；不发生新副本材料卡死基础经济或挂机取代全部主动内容。

### P7：最小丹药与功法

只录入实际需要并已核验来源的条目。先确定项目效果、再选参考名称和数据映射；新丹药若需要药材和设施，作为一个完整小链条验证，不能仅新增无法获得的物品。

验收：配方合法、数量与计时、库存不足不扣半款、加速与突破效果、永久学习与局内强化分离。若核心循环已满足且丹药无独立作用，可延期本阶段；须由负责人确认移出交付范围，而不是默认为未完成也算完成。

### P8：平衡、回归与Windows交付

运行获批范围需要的完整回归与旧档迁移，测试和导出串行。做Windows独立包启动与真人鼠标键盘试玩，两种尺寸界面检查，记录性能、奖励、时间和已知问题。

## 9. 代码职责与存档约束

优先检查现有位置：scripts/core/game_state.gd负责持久游戏规则；save_manager.gd负责保存与离线；scripts/data各目录配置负责公式/内容；scripts/main/main.gd负责主界面交互；scripts/world负责经营地图；tests/run_all_tests.ps1负责现有回归入口。

## 10. 验收、交付与停止条件

每阶段交付：关联Issue、批准范围、改动文件、存档影响、测试结果、实际截图/试玩入口、已知问题、待负责人检查项。分清代码完成、自动测试、图形运行、Windows导出、人工验收。

重点自动检查：资源守恒与缺粮恢复；建造合法性与失败原子性；活动互斥与装备唯一性；旧档迁移与错误输入；局内效果上限；结算幂等；保存失败、退出和恢复；在线/离线时间不重算。

重点人工检查：自由建造可理解且点选准确；移动与受伤反馈清楚；攻击能靠操作躲避；强化能改变打法；失败后知道如何提升；第一次带回奖励确实产生发展；界面不遮住攻击预警。

遇到以下情况暂停受影响阶段、调查后调整：旧档字段或身份丢失；进阶材料无来源；暂停/重读可刷奖励；关键数值需改变但未获批准；阶段需要扩图、多角色AI、全图重制或额外依赖才能继续。不要以增加新系统掩盖基本循环问题。

最终交付标准：完成至少两轮宗门准备—主动副本—结算提升；生产、养成、战斗均有不可替代的作用；失败可恢复；旧数据受保护；Windows可独立运行；负责人验收明确。
