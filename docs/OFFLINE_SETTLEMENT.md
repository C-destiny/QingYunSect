# V0.5 离线结算契约

## 时间基线

- 每次成功替换主存档后，该存档的 `saved_at_unix` 成为新的可信离线起点。
- 读取主档或备份时，只使用实际读取成功文件内的时间，不使用损坏主档的时间。
- `now < saved_at` 判定为系统时间倒退，不产生离线收益。
- 间隔不足1秒不产生结算；有效间隔最多取28,800秒（8小时）。
- 超过上限时保留真实间隔和“已截断”标记，界面必须向玩家说明。

## 离线窗口结构

- `saved_at_unix`：成功读取存档的保存时间。
- `now_unix`：本次读取使用的当前时间快照。
- `raw_seconds`：未经上限处理的非负间隔。
- `effective_seconds`：实际用于模拟的秒数。
- `eligible`：是否允许进入收益计算。
- `truncated`：是否受到8小时上限限制。
- `reason`：`eligible`、`capped`、`too_short`、`clock_moved_back`或`missing_anchor`。
- `settlement_id`：由保存起点与本次时间组成的追踪标识；它是审计信息，不单独承担最终防重职责。

## 状态转换

1. 读取并完整校验主档；失败时再尝试备份。
2. 只有游戏状态成功导入后才根据该文件时间生成离线窗口。
3. 时间窗口交给后续离线模拟器生成收据。
4. 后续原子结算任务负责应用结果、持久化新锚点并清除窗口。
5. 任一步失败不得部分修改游戏状态或伪造“已领取”。

## 模拟顺序与性能

- 施工、升级和招募的最近完成时间把离线时段切成有限段；每段先按当时有效建筑和人口结算修炼、生产与粮耗，再推进计时活动。
- 灵谷按正常效率阶段和缺粮50%效率阶段解析计算；资源点基础速率集中在 `ResourceCatalog`，在线与离线共用。
- 自动战斗根据伤害、剩余生命、回合时间和2秒等待直接求完整胜场；不按离线秒数逐帧循环。
- 离线期间只重复存档中已经选中的关卡。胜利可以按既有规则解锁下一关，但不会自动切换过去。
- 同一收据中，经营消耗先结算，战斗奖励随后回流库存；该固定顺序用于避免不同机器因帧顺序得到不同结果。

## 原子应用

- `GameState.apply_offline_progress`生成一张包含资源净变化、粮耗、修为、胜场、施工/升级/招募完成数的收据。
- `SaveManager.settle_pending_offline_progress`先保留完整内存快照，再应用收据并执行安全保存。
- 保存成功后清除待结算窗口；再次调用不会重复领取。
- 保存失败时完整恢复快照并保留窗口，允许之后安全重试。

## 兼容性

V0.4正常存档已有 `saved_at_unix`，可以直接生成窗口。更早但有效、且缺少该字段的存档仍允许读取，但本次原因标记为 `missing_anchor`，不追溯发放收益；下一次成功保存后自动拥有时间基线。`SAVE_VERSION`暂时保持1。
